# PRD: 6.4 Lập trình Cặp cùng AI (AI Pair Programming)

> **Dự án:** TripMind AI – Ứng dụng lập kế hoạch du lịch thông minh bằng AI
> **Môn học:** Chuyên đề 4: AI Product Development
> **Chương:** 6 – Lập trình cùng AI · Mục 6.4
> **Phiên bản:** 1.0 · **Ngày cập nhật:** 29/09/2026

## Introduction

Tài liệu trình bày mô hình **lập trình cặp cùng AI (AI Pair Programming)** — con người
và AI làm việc như một cặp lập trình viên, luân phiên vai trò "driver" (viết code) và
"navigator" (định hướng, rà soát). Minh hoạ bằng chính quá trình xây dựng TripMind AI.

## Goals

- Định nghĩa mô hình pair programming với AI và phân vai.
- Minh hoạ một phiên pair thực tế khi làm TripMind AI.
- Rút ra nguyên tắc để pair với AI hiệu quả.

## User Stories

### US-001: Phân vai Driver / Navigator
**Description:** Là một developer, tôi muốn hiểu ai làm gì khi pair với AI.

**Acceptance Criteria:**
- [ ] Định nghĩa vai Driver và Navigator
- [ ] Nêu khi nào AI làm driver, khi nào con người làm driver

### US-002: Minh hoạ phiên pair thực tế
**Description:** Là một người học, tôi muốn xem một phiên pair cụ thể từ đầu đến khi chạy được.

**Acceptance Criteria:**
- [ ] Có kịch bản phiên pair (yêu cầu → code → chạy → sửa)
- [ ] Gắn với tính năng thật (ví dụ Priority hoặc auth)

### US-003: Nguyên tắc pair hiệu quả
**Description:** Là một developer, tôi muốn nguyên tắc để pair với AI không mất kiểm soát.

**Acceptance Criteria:**
- [ ] Danh sách nguyên tắc rõ ràng
- [ ] Nhấn mạnh vai trò quyết định của con người

## Functional Requirements

- **FR-1:** Định nghĩa vai trò Driver/Navigator trong pair với AI.
- **FR-2:** Kịch bản một phiên pair thực tế của TripMind AI.
- **FR-3:** Nguyên tắc pair hiệu quả.

## Non-Goals

- Không bàn quy trình tổng thể end-to-end (thuộc 6.5).
- Không so sánh công cụ cụ thể.

## Technical Considerations

- Pair với AI hiệu quả khi vòng lặp **ngắn**: yêu cầu nhỏ → code → chạy thử → phản hồi.
- Con người giữ vai **navigator** ở các quyết định kiến trúc/nghiệp vụ.

## Success Metrics

- Mỗi vòng pair kết thúc bằng code chạy được hoặc bài học rõ ràng.
- Con người luôn hiểu và kiểm soát được code sinh ra.

## Open Questions

- Khi nào nên để AI tự chạy nhiều bước, khi nào cần dừng lại xác nhận?
- Làm sao tránh "trôi" theo AI mà mất hiểu biết về code?

## Phụ lục A – Phân vai trong pair với AI

| Vai | Ai đảm nhận | Nhiệm vụ |
|-----|-------------|----------|
| **Driver** | Thường là AI | Viết code cụ thể, gõ nhanh, sinh boilerplate |
| **Navigator** | Thường là con người | Định hướng thiết kế, rà soát, quyết định nghiệp vụ |

Vai trò **luân phiên**: khi cần quyết định kiến trúc, con người làm driver (viết đặc tả,
chọn phương án); khi hiện thực hóa chi tiết, AI làm driver còn con người rà soát.

## Phụ lục B – Kịch bản một phiên pair thực tế

Phiên pair xây dựng tính năng **đổi Priority hoạt động** (Chương 4 → code):

| Bước | Người (Navigator) | AI (Driver) | Kết quả |
|------|-------------------|-------------|---------|
| 1 | "Cần endpoint đổi priority, phải kiểm ownership" | Sinh `PATCH /activities/:id` có JOIN kiểm user | Code endpoint |
| 2 | Rà soát: thiếu ràng buộc giá trị priority | Thêm `CHECK (priority IN ...)` ở schema | Schema an toàn hơn |
| 3 | "Frontend cần đổi priority optimistic" | Sinh hàm `changePriority` cập nhật UI trước, gọi API sau | UX mượt |
| 4 | Chạy thử → phát hiện 500 error | Phân tích log, sửa lỗi bcrypt (xem 6.3) | Chạy được |
| 5 | Xác nhận: test lại toàn luồng | Đề xuất các lệnh curl kiểm chứng | ✓ Pass |

**Trích code là kết quả của phiên pair trên** (`apps/web/src/App.tsx`):

```tsx
async function changePriority(act: Activity, priority: string) {
  // Cập nhật lạc quan trên UI; nếu đã lưu (có id) thì gọi API.
  setItin((cur) => ({
    ...cur,
    itinerary: cur.itinerary.map((day) => ({
      ...day,
      activities: day.activities.map((a) =>
        a === act ? { ...a, priority: priority as Activity["priority"] } : a),
    })),
  }));
  if (act.id) {
    try { await api.updatePriority(act.id, priority); }
    catch (err) { onError((err as Error).message); }
  }
}
```

## Phụ lục C – Nguyên tắc pair với AI hiệu quả

1. **Vòng lặp ngắn:** yêu cầu nhỏ → code → chạy thử → phản hồi. Tránh để AI làm quá
   nhiều bước rồi mới kiểm tra.
2. **Con người là navigator ở quyết định lớn:** kiến trúc, nghiệp vụ, bảo mật do con
   người định hướng; AI hiện thực chi tiết.
3. **Luôn chạy thử:** không nhận code chỉ vì "trông đúng" — phải verify (xem 6.1, 6.3).
4. **Hiểu code mình nhận:** nếu không hiểu đoạn AI viết, hỏi lại hoặc yêu cầu giải
   thích — tránh "trôi" theo AI.
5. **Ghi lại quyết định & bài học:** để lần sau tái sử dụng (như tài liệu này).

> **Bài học:** pair với AI nhanh và mạnh, nhưng giá trị chỉ bền khi **con người vẫn
> hiểu và kiểm soát** được sản phẩm — AI mở rộng năng lực, không thay thế trách nhiệm.
